# Decisions

## Decided (2026-11-24)

| # | Decision | Reason |
| :--- | :--- | :--- |
| D1 | **Python + FastAPI + SQLite + Jinja/HTMX** | One language. Async suits many parallel LLM calls. No JS build step, and a single-file DB. |
| D2 | **Local, single-user app; no login** | It's a research tool. Avoids auth and multi-tenant isolation. Tokens stay on the user's machine. |
| D3 | **API tokens encrypted at rest (Fernet), with an environment override** | A plain-text DB file is too easy to leak by sharing `data/`. |
| D4 | **Seed = questions + context only** (no answers, no human scores) | Chosen by the team. Human scores can be imported later as a validation set (backlog). |
| D5 | **UI and docs in English** | Wider audience. Matches the wiki topic pages. |
| D6 | **Own thin provider adapters, no LiteLLM/LangChain** | 3 adapters cover all target APIs. This gives exact raw request/response recording and fewer dependencies. Revisit if many more native APIs are needed. |
| D7 | **Keep the study's 1–5 overall scale**, plus censorship type, balance, and depth | Comparable with the study's ranking. The extra fields capture the study's findings (soft vs. hard censorship; shallow ≠ neutral). |
| D8 | **One response = one judgement** (per judge); turn 2 is judged with the partner's answer as context | Simple, traceable, and allows multiple judges later. |
| D9 | **Run snapshots** (prompt text, model ID, and config copied into the run) | Editing topics or models must not change past results. |
| D10 | **The judge doesn't see the evaluated model's name** | Reduces brand bias. |
| D11 | Seed country code **`ARAB`** for "Arab states" (Saudi Arabia topics, Falcon from the UAE) | Matches the study's grouping. Users can add finer codes. |
| D12 | **Enum-like columns are plain TEXT**; the value sets live as `StrEnum`s in `app/models/base.py` and are validated in services (M0) | SQLAlchemy `Enum` stores member *names*, not values, and makes adding a value a migration. Stored values match the docs exactly (`criss_cross`, `20th_century`). |
| D13 | **Model snapshot lives on `response`** (`model_id_snapshot`, `display_name_snapshot`) rather than on `run_item` (M0) | A criss-cross item has two models; one answering model per response is the natural place for the snapshot rule. |
| D14 | **Datetimes are timezone-aware UTC** (sqlmodel `UTCDateTime`); naive datetimes are rejected on write (M0) | Avoids mixed naive/aware comparisons in the run engine. |
| D15 | **Log redaction is done in the formatter** (`app/log.py`), not a `logging.Filter`; uvicorn runs with `log_config=None` so its logs go through it (M0) | The formatter sees the final text including formatted args and tracebacks, which a filter would miss. |
| D16 | **Pico.css classless build** (2.0.6) and htmx 2.0.4 vendored in `app/web/static/` (versions in `VENDORED.md`) (M0) | Matches "classless" in 02-architecture; no CDN, so the app works offline. |
| D17 | **Migrations at repo root** (`migrations/`), located from the package path; `histbias init` runs `alembic upgrade head` programmatically (M0) | Matches the planned layout. Requires the project to be installed in editable mode (the `uv sync` default). |
| D18 | **The first prompt row is the default prompt** in the topic form (no radio button) (M1) | Works with HTMX-added rows without client-side index bookkeeping. Stored as `prompt.is_default`; the default always sorts first. |
| D19 | **Empty default prompt is filled from the template** ("Tell me about {title}" / "Express yourself about {title}"); an empty **English** criss-cross follow-up gets the study's text. Other languages must give their own follow-up (M1) | Implements the "pre-filled" prompt from 04-ui without JS, and never puts English turn-2 text into a non-English conversation. |
| D20 | **New topic slugs follow the seed style**: `{country}-{era}-{title}` for internal, `{country}-vs-{country}-{title}` for criss-cross, using country names; `-2`, `-3`… on collision. Slugs can't be edited (M1) | Slugs are the identity for import/export; editing them would break round-trips and re-imports. |
| D21 | **Delete = hard delete only if no run references the topic; otherwise it is archived** (M1) | 04-ui UX rule. Archived topics are hidden from the list (filter "Show archived") and from the run wizard. |
| D22 | **Import preview keeps the upload in `data/imports/<random>.yaml`** until confirmed (pruned after 24 h) (M1) | Starlette limits non-file form fields to 1 MB, so the 5 MB file can't round-trip through a hidden field. The token is validated as 32 hex characters. |
| D23 | **CSRF: double-submit cookie (`histbias_csrf`, HttpOnly, SameSite=Strict) + `Origin` check**, enforced by one app-wide dependency. Forms send `csrf_token`; HTMX sends `X-CSRF-Token` from `hx-headers` on `<body>`. A missing `Origin` is allowed (non-browser clients), but the token is always required (M1) | 07-security. Added in M1 because it is the first milestone with forms. |
| D24 | **Topic context is rendered through the same sanitizing Markdown renderer as model output** (`app/web/markdown.py`: markdown-it with HTML off + nh3, http/https/mailto links only) (M1) | Imported YAML is untrusted too. Source URLs are restricted to http(s) at validation time because they are rendered as links. |
| D25 | **Anthropic adapter uses raw httpx, not the `anthropic` SDK** (M2) | Same reason as D6: the exact request/response bodies are stored, and tests use `respx`. 06-providers allowed either. |
| D26 | **No temperature to Anthropic by default; no server-side refusal fallbacks** (M2) | Current Claude models accept only default sampling and API version 2026-10-21 rejects `temperature`. A fallback model answering would invalidate a censorship measurement. |
| D27 | **GigaChat adapter implemented in M2** (the roadmap listed only mock/openai/anthropic) (M2) | It is a preset and a study model; it reuses the OpenAI-compatible adapter plus an OAuth step (~80 lines). |
| D28 | **Environment override names**: `HISTBIAS_KEY_<PROVIDER NAME, non-alnum → _>`, extra secret fields as `…__<FIELD>` (e.g. `HISTBIAS_KEY_YANDEX_AI_STUDIO__FOLDER_ID`) (M2) | Deterministic from the provider name; shown on the provider form. |
| D29 | **Secrets never leave memory in clear**: `Secret` hides its value in repr; error messages and stored error bodies are scrubbed of the key and key-like values; provider `extra` rejects secret-looking setting names; base URLs may not contain credentials or a query string (M2) | 07-security "never leak tokens", including keys pasted into the wrong field or echoed back by an API. |
| D30 | **Key hint only for keys ≥ 12 characters** (M2) | Showing the last 4 characters of a short secret reveals too much of it. |
| D31 | **Content blocks are results**: 403 with "unsafe" (Qianfan) → `ProviderRefused`, not an auth error; `REFUSAL_FINISH_REASONS = {content_filter, refusal, blacklist}` (M2) | Found while verifying presets; needed by the M3 refusal heuristic. |
| D32 | **The encryption key is created by `histbias init` and on app start**; if it is invalid the app still starts and the API keys page shows the problem (M2) | 07-security: "doesn't crash". |
| D33 | **Model settings are frozen in `run.config["models"]`** (model ID, display name, effective temperature, max tokens, system prompt); the executor reads them from there, not from `llm_model`. The provider's base URL and key are read live (M3) | Snapshot rule (D9) for everything that shapes the answer. Keys must never be copied, and a rotated key should apply to a paused run. |
| D34 | **A draft stores only the wizard settings; items and the snapshot are made when it starts** (M3) | A draft is a saved selection. Planning at start uses the current prompts and keys, and an edited draft has nothing stale to clean up. |
| D35 | **Retries: at most 3 calls per item** for 429, 5xx, 408 and timeouts, with exponential backoff (2 s, 4 s, ×1–1.25 jitter, at least `Retry-After`, at most 120 s). A waiting item is `pending` and holds no slot; the wait is kept in memory, so after a restart it retries at once. Auth and other 4xx errors are not retried. "Retry failed" resets the attempt count (M3) | Keeps slow providers from blocking others, and needs no extra column. |
| D36 | **Run end state:** `failed` if every finished item is an error and none was answered, else `completed` (errors are shown with "Retry failed"). **Cancel** turns pending items into `skipped`; calls already in flight finish and are kept (M3) | A wrong key fails the whole run visibly; partial results are still results. |
| D37 | **`response.raw` holds the request body too** (`{"request", "response", "notes"}`) (M3) | D6 promised exact request recording; `messages` alone loses temperature, max tokens and the adapter's notes (e.g. "temperature not sent"). |
| D38 | **Content blocks (`ProviderRefused`) are stored as a response** with empty text, the error message and `refusal_detected = true`; the item is `answered`. The phrase heuristic only searches the first 400 characters (M3) | A block is a result (D31). Refusals come first; searching the whole text flags long answers that say "I cannot verify…" later on. |
| D39 | ~~**Criss-cross topics are listed but not selectable in the wizard until M4**~~ Superseded in M4: they are selectable (M3) | Keeps the "Start run with selected" flow from the Topics page working. |
| D40 | **SQLite runs in WAL mode with `busy_timeout = 10 s`** (M3) | The worker writes while web requests read and write; without it, concurrent writes fail with "database is locked". |
| D41 | **Open questions 2 and 3 decided as proposed:** temperature defaults to each model's own setting (else the provider default) with an optional fixed value, recorded in the run config; internal topics default to all selected models, with "only home-country models" as an option (M3) | Matches the proposals; both are visible in the run's Config section. |
| D42 | **A minimal Response page (`/responses/{id}`) ships in M3** (prompt, sanitized answer, refusal heuristic and its reason, tokens, latency, raw bodies) (M3) | Needed to check answers before the judge and the full response detail (M5/M6) exist. |
| D43 | **Manual pairs apply to every selected criss-cross topic** (one list of model A × model B rows in the wizard); both models must also be ticked, and a model can't be paired with itself. Automatic pairing puts the topic's first country on side A (M4) | 05-methodology only says "the user picks the pairs". One global list keeps the wizard simple; per-topic pairs can come later if needed. |
| D44 | **Every answer is stored as soon as its call returns**; a retry or restart repeats only the missing calls (A1/B1 are never asked twice). A criss-cross item gets the attempt budget twice (3 per turn) (M4) | Re-asking a model that already answered would change the conversation the partner sees, and wastes calls. |
| D45 | **A blocked or empty turn-1 answer ends that side's conversation**: the blocked model gets no turn 2, and neither does its partner (nothing to comment on). The item is `answered` and the reason is kept in `run_item.error`. A refusal that has text is passed on like any answer (M4) | An empty assistant message is rejected by several APIs, and asking for comments on nothing produces no data. Refusal text is exactly what the partner should react to. |
| D46 | **Concurrency limits count parallel calls**: a criss-cross item takes 2 slots (both sides of a turn run in parallel). An item that needs more slots than a limit still runs when nothing else holds that limit (M4) | Keeps per-provider limits honest for pairs, without deadlocking at a limit of 1. |
| D47 | **"Native language" for a criss-cross topic means the native languages of both countries**, each asked if the topic has a prompt in it (M4) | A pair spans two countries; both perspectives' languages are relevant. |
| D48 | **Pause and cancel are also checked between turn 1 and turn 2**: a paused item goes back to the queue without using an attempt; a cancelled one is `skipped` and keeps its turn-1 answers (M4) | "The worker checks them before every call" (02-architecture). |
| D49 | **The response page shows the item's 2×2 grid** (A1 B1 / A2 B2) for criss-cross responses, with the selected answer's full conversation below (M4) | The roadmap's "Response detail shows the 2×2 grid", using the M3 response page (D42). |
| D50 | **Failed judgements are stored** (migration 0002: score fields nullable, plus `error` and `repaired`); a later successful judgement replaces the failed row (M5) | The raw output of a failed judge call is evidence (e.g. a judge refusing to evaluate an answer about its own country). The UNIQUE(response, judge, rubric) rule still holds. |
| D51 | **Judging is a second phase of each item, run by the same worker**: an `answered` item in a run with a judge is claimed again for judging. Judge calls use the judge's provider slots (1 per internal item, 2 for a criss-cross item's 4 responses). An item is `judged` when every response has a valid judgement, else `judge_failed` (M5) | Judging starts as soon as an item's answers exist, respects provider limits, and resumes after a restart like answering. |
| D52 | **Judge API errors**: 429/5xx/timeouts are retried (3 attempts, counted in memory, so a restart gives a fresh budget); other errors (e.g. a bad key) make the item `judge_failed`. A content block by the judge's API is a failed judgement. "Retry failed" re-queues `judge_failed` items to the judge only; their answers are not asked again (M5) | `run_item.attempts` keeps counting answer attempts. |
| D53 | **Strict judge validation**: integer scores only (`"4"` and `4.5` are rejected), real booleans, extra keys ignored; JSON inside a code fence or prose is accepted (M5) | Lenient coercion would hide a judge that doesn't follow the format; the repair retry handles honest mistakes. |
| D54 | **The judge's topic data (title, era, countries, context) is read when judging**, not frozen at run start; the exact prompt sent is stored in `judgement.judge_prompt` (M5) | Judging follows the answers within seconds or minutes, and the stored prompt records exactly what the judge saw. |
| D55 | **Judge warnings** in the wizard and run config: the judge is a tested model, comes from the same provider as a tested model, or comes from a country in a selected topic. Default judge: none, so the user chooses explicitly (M5) | 05-methodology, "Judge self-preference". |
| D56 | **`histbias serve` applies pending migrations on start** (M5) | M5 adds the first migration after the initial one; existing databases must not break after an update. |
